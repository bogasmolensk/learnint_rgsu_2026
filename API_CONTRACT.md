# API контракт: Equipment Request Service

## Общие правила
- Все ответы в формате JSON (Content-Type: application/json).
- Даты во всех запросах и ответах — ISO 8601 в UTC, формат: 2026-10-12T15:30:00Z.
- Аутентификация: заголовок Authorization (появится на след. неделях).
  Пока пользователь определяется тестовыми данными / заголовком X-User-Id для демо.
- Ошибки возвращаются в виде: { "error": "CODE", "message": "текст" } с соответствующим HTTP-статусом.

## Разделение полей (клиент и сервер)
- КЛИЕНТ передаёт (в теле запроса): equipmentName, quantity, justification,
  (при отклонении) comment.
- СЕРВЕР назначает сам, клиент НЕ может их прислать ПРИ СОЗДАНИИ: id, authorId, status,
  decisionComment (кроме случая отклонения), createdAt, updatedAt, version
  (при создании сервер ставит version = 0). Любая попытка прислать эти поля при создании
  отклоняется (400).
- ИСКЛЮЧЕНИЕ для version при изменении: во всех изменяющих запросах (редактирование,
  отправка, отмена, одобрение, отклонение) клиент ОБЯЗАН прислать поле version в теле —
  то значение, которое получил в последнем ответе сервера. Это не назначение версии,
  а подтверждение актуальности данных (см. «Работа с версиями»).

## Работа с версиями (защита от одновременного изменения)

Поле `version` в БД защищает заявку от конфликтов, когда два пользователя одновременно
меняют одну запись.

1. Клиент получает заявку (`GET` или ответ `POST`/`PATCH`). В теле карточки есть поле
   `version` (например, `0`). Клиент запоминает это значение.
2. Клиент хочет изменить заявку. Он обязан положить полученное `version` в тело запроса
   на изменение.
3. Сервер сравнивает присланное `version` с текущим значением в БД:
  - Совпадает → выполняет изменение, увеличивает `version` на 1, возвращает обновлённую
    карточку с новой версией.
  - Не совпадает (кто-то другой успел изменить раньше) → НЕ сохраняет изменения,
    возвращает `409 Conflict` с кодом `VERSION_CONFLICT`.
4. Если поле `version` отсутствует в изменяющем запросе — сервер возвращает
   `400 Bad Request` с кодом `VALIDATION_ERROR`.
5. Получив `409 VERSION_CONFLICT`, клиент должен перезагрузить заявку (`GET`) и повторить
   действие с новой версией.

## Таблица операций

| # | Операция | HTTP | URL | Тело запроса (клиент) | Успешный ответ | Ошибки |
|---|---|---|---|---|---|---|
| 1 | Создание заявки | POST | `/api/v1/requests` | `{equipmentName, quantity, justification}` | 201 + полная карточка (DRAFT, version=0) | 400, 401, 403 |
| 2 | Чтение одной | GET | `/api/v1/requests/{id}` | — | 200 + полная карточка (текущий version) | 400, 401, 403, 404 |
| 3 | Список заявок | GET | `/api/v1/requests?scope=&status=&from=&to=&page=&size=` | — | 200 + объект пагинации (см. выше) | 401 |
| 4 | Редактирование | PATCH | `/api/v1/requests/{id}` | `{equipmentName?, quantity?, justification?, version}` | 200 + обновлённая карточка (version+1) | 400, 401, 403, 404, 409 |
| 5 | Отправка на рассмотрение | POST | `/api/v1/requests/{id}/submit` | `{version}` | 200 + карточка (UNDER_REVIEW, version+1) | 400, 401, 403, 404, 409 |
| 6 | Отмена | POST | `/api/v1/requests/{id}/cancel` | `{version}` | 200 + карточка (CANCELLED, version+1) | 400, 401, 403, 404, 409 |
| 7 | Одобрение | POST | `/api/v1/requests/{id}/approve` | `{version}` | 200 + карточка (APPROVED, version+1) | 400, 401, 403, 404, 409 |
| 8 | Отклонение | POST | `/api/v1/requests/{id}/reject` | `{comment, version}` (comment обязательно непустое) | 200 + карточка (REJECTED, version+1) | 400, 401, 403, 404, 409 |
| 9 | История | GET | `/api/v1/requests/{id}/history` | — | 200 + массив записей истории | 400, 401, 403, 404 |

Семантика scope (разделение по ролям, строка 3 таблицы): для роли «Сотрудник» список всегда фильтруется по автору — возвращаются только его заявки,
параметр scope игнорируется (чужие заявки сотрудник не видит и не может запросить, это не 403, а фильтрация на уровне запроса).
Для роли «Ответственный» scope принимает значения: all (все заявки), mine (его собственные как автора), pending (статус «На рассмотрении», автор — не он, то есть очередь на его решение). 
Параметры from/to — диапазон дат создания в ISO 8601 UTC.

Пагинация списков:
метод получения списка заявок (GET /api/v1/requests) поддерживает пагинацию для ограничения объема данных.
Параметры запроса:
page (int, default=0): Номер страницы (начинается с 0).
size (int, default=20): Количество элементов на одной странице (max 100).
Структура ответа: Возвращается объект-обертка, содержащий метаданные и массив данных.

```json
{
"content": [ ... ],      // Массив карточек заявок
"totalElements": 150,    // Общее количество найденных заявок
"totalPages": 8,         // Всего страниц
"currentPage": 0,        // Текущая страница
"pageSize": 20           // Размер страницы
}
```

`400` = невалидные данные / пустой комментарий / отсутствие поля version в изменяющем
запросе (VALIDATION_ERROR) / попытка прислать служебное поле при создании / некорректный формат идентификатора в пути (INVALID_ID_FORMAT).
`401` = не авторизован.
`403` = нет прав (не автор / не ответственный / ответственный трогает свою заявку).
`404` = заявка не найдена.
`409` = два разных случая, различаются по коду в теле:
- VERSION_CONFLICT — присланное version не совпало с текущим в БД (данные изменил
  кто-то другой); клиент перезагружает заявку (GET) и повторяет действие;
- INVALID_STATUS_TRANSITION — операция запрещена текущим статусом заявки
  (редактирование не-DRAFT, одобрение уже одобренной, отмена из конечного статуса).

## Примеры JSON

### POST /api/v1/requests — создание
Запрос:
```json
{ "equipmentName": "Монитор 27\"", "quantity": 2, "justification": "Для нового сотрудника" }
```
Ответ 201:
```json
{
  "id": 1,
  "authorId": 1,
  "equipmentName": "Монитор 27\"",
  "quantity": 2,
  "justification": "Для нового сотрудника",
  "status": "DRAFT",
  "decisionComment": null,
  "createdAt": "2026-10-13T12:37:00Z",
  "updatedAt": "2026-10-13T12:37:00Z",
  "version": 0
}
```

### POST /api/v1/requests/1/reject — отклонение (комментарий обязателен)
Запрос:
```json
{ "comment": "Недостаточно обоснования, уточните задачу", "version": 1 }
```
Ответ 200:
```json
{
  "id": 1,
  "authorId": 1,
  "equipmentName": "Монитор 27\"",
  "quantity": 2,
  "justification": "Для нового сотрудника",
  "status": "REJECTED",
  "decisionComment": "Недостаточно обоснования, уточните задачу",
  "createdAt": "2026-10-13T12:37:00Z",
  "updatedAt": "2026-10-13T13:00:00Z",
  "version": 2
}
```

### GET /api/v1/requests/1/history — история (event-log: каждый переход отдельной строкой)
Ответ 200:
```json
[
  { "changedBy": 1, "previousStatus": null,           "newStatus": "DRAFT",        "comment": null,                          "createdAt": "2026-10-13T12:37:00Z" },
  { "changedBy": 1, "previousStatus": "DRAFT",        "newStatus": "UNDER_REVIEW", "comment": null,                          "createdAt": "2026-10-13T12:40:00Z" },
  { "changedBy": 2, "previousStatus": "UNDER_REVIEW", "newStatus": "REJECTED",     "comment": "Недостаточно обоснования",    "createdAt": "2026-10-13T13:00:00Z" }
]
```


### Ошибка 409 INVALID_STATUS_TRANSITION — попытка редактировать отправленную заявку
Ответ:
```json
{ "error": "INVALID_STATUS_TRANSITION", "message": "Редактирование запрещено: заявка не в статусе DRAFT" }
```

### Ошибка 409 VERSION_CONFLICT — присланная version устарела
Ответ:
```json
{ "error": "VERSION_CONFLICT", "message": "Заявка была изменена другим пользователем. Обновите данные и повторите." }
```
